# YVR 应用移植到 Quest

以目标 APK 的调用和实机证据决定兼容方案。完成用户要求的功能，并交付经过签名校验的 APK 与必要支持包。这份 Skill 综合 DeepSeek 早期记录、后续源码和证据，以及用户直到 build210 的测试反馈；私有属性编号、二进制地址和性能设置均有适用范围，不是全部 YVR 应用的规格。原记录中的实验和结论分别审核，纠错与未证实部分见 [references/history-corrections.md](references/history-corrections.md)。

## 从当前现场继续

先读工作区入口及最新交接，确认原包/解包树、源码、工具链、已安装版本、已验收功能和本轮问题。旧交接中的猜测、现场状态和后续计划可能已经过时，优先采用可复核的最新证据。

记录原 APK、待修改原库和最终产物的 SHA256，识别包名、版本、min/target SDK、ABI、Unity/IL2CPP 版本、清单服务/provider、DT_NEEDED 及实际 YVR 调用。区分镜像提取的参考 APK、原始 APK、未签名构建、签名交付；文件名“SDK”或“final”不证明来源或可安装性。

本机影院的准确入口、构建命令和保留文件见 [references/cinema-build210.md](references/cinema-build210.md)。新应用应重新发现相应信息。

从原包开始时，读 [references/bootstrap-dependencies.md](references/bootstrap-dependencies.md)：区分真正的 VR/6DoF 内容与二维面板，识别系统 UID/外部 SDK/原 runtime 依赖，建立 ASCII 构建树和 Quest VR 入口。已完成的迁移只读取与新问题相关的部分。原记录“可以放弃二维应用”是早期范围，用户后来已要求并验收 Shizuku 巨幕容器；不沿用过时的功能排除。

## 实施约束

- apktool/aapt2 的构建树、临时产物和输出使用纯 ASCII 路径。本案例固定 `E:\yvrwork`，中文资料目录用于读取和交接。
- C 改动使用可审核补丁或唯一锚点且校验命中数；不用 PowerShell `-replace`。锚点、原字节或版本不匹配就停止该补丁，不继续生成假成功产物。
- Android 原生库链接启用 `-Wl,--no-undefined`。检查编译退出码、导出符号和依赖；编译成功不等于设备能加载。
- 新拦截既考虑动态符号导出，也考虑 `xrGetInstanceProcAddr`。私有 API 要明确 ABI、输出结构、容量和状态语义，不能只返回成功。
- C++ 返回 `const float&` 等引用时 ABI 返回地址，不能改成返回标量。IL2CPP 值类型返回值需 unbox；诊断方法必须存在、签名准确、异常受检，并在该操作允许的线程执行。
- 优先修正边界数据或缺失平台接口。永久强制 focus/init、全局 gamma 或按猜测旋转，会掩盖故障并破坏其他功能。
- 修改原生二进制前，从 ELF 映射 RVA 到文件偏移，反汇编确认函数和原指令。可用 [scripts/patch_exact_bytes.py](scripts/patch_exact_bytes.py) 在校验完整输入 SHA256、原字节、边界及不重叠后生成独立输出；它不判断指令语义或自动推断偏移。
- 当前影院使用的 shim/容器含该版本专用假设。迁移到另一 APK 前复核 action/会话数量、资源生命周期、私有接口和颜色写入方式；不要把整库替换当作通用安装步骤。
- 当前 shim 的通用 YVR 桩仍存在返回成功但输出不完整的分支，注释也有过时内容；具体已修复的眼位/输入/刷新率接口与通用桩区分处理。新应用需逐项检查它实际调用的接口，而不是以影院验收代替所有私有接口语义验证。

## 构建与验收

按用户所需功能构建候选；调试探针单独开关，交付版关闭诊断命令、读回、逐帧打印和测试界面。保留源码、原库备份和补丁清单。与支持包的签名权限、sharedUserId、查询依赖一起检查，不随意改变所有包的 target SDK 或包名。

签名后执行 APK 签名及对齐验证，再校验交付副本哈希。安装用正确设备的 `adb install -r -g`，随后验证进程、XR 会话和渲染。升级签名冲突先查原因；不要为了“安装成功”自动卸载用户应用。保留正常边界、锁屏及常亮设置。本机旧 `run.ps1` 只使用 `-BuildOnly`，其自动安装分支会设置过时的 `guardian_pause=1`。

验收与本轮改动有关的真实行为：双眼/头部跟随；左右手输入、角度与菜单；视频首帧/声音/暂停；封面；二维应用的列表/图标/点击/滑动/返回及影院焦点；颜色；实际分辨率与运行帧率。ADB 的 Success、注入 accepted 或单张截图不能替代这些证据。需要人戴头显操作时，提一个明确、简短的测试请求，同时继续独立日志检查。

报告“已日志验证”“已用户验收”“尚未验证”的区别。120Hz 请求成功不保证片源或第三方应用每秒生成 120 帧；短时运行不能证明长期温控表现。保留必要支持包，注明 Shizuku 的重启要求和功能范围。

清理用户要求的历史构建时，先枚举并验证绝对目标路径，再按具体文件删除，保留原始/提取 APK、工具、源码、证据与最终交付。不要把清理脚本或过去任务的授权当作新任务必须执行的步骤。
